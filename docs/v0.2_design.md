# Name That LLM — V0.2 Design: Qwen Model Size and Ensemble Study

**Status:** Experiment design  
**Builds on:** The current local MVP implementation in `docs/mvp_design.md` and `docs/mvp_implementation.md`  
**Scope:** Add Qwen3-1.7B and Qwen3-4B classifiers, then assess SmolLM3-3B Base, Granite 4.0 H Micro Base, Google EmbeddingGemma 2, Gemma 4 E4B, and Ministral 3 3B as additional model-family candidates. Train LoRA causal models for 10 epochs with per-epoch validation; use frozen feature baselines for embedding/multimodal families and compare all completed models and ensembles.

## 1. Goal

Measure whether Qwen3-1.7B, Qwen3-4B, SmolLM3-3B, and Granite 4.0 H Micro improve author classification over the existing Qwen3-0.6B, SVC, CatBoost + Stylometry, and UltraBERT-380M models, either individually or as ensemble members. Also assess EmbeddingGemma 2, Gemma 4 E4B, and Ministral 3 3B as additional candidates and test error complementarity. Keep the data split and validation rows fixed so model comparisons use the same examples.

This version is a model-size and ensemble study. It does not introduce new data, new labels, or a new evaluation split.

## 2. Current benchmark to preserve

The current implementation has one deterministic, prompt-grouped 80/20 split. The Data Factory chooses among 1,000 grouped candidates based on row fraction and label balance, using IDs, prompt groups, and labels only.

- Official training data: 2,699 rows, 18 labels, about 150 prompt groups.
- Train: 2,159 rows from 120 prompt groups.
- Validation: 540 rows from 30 prompt groups, exactly 30 rows per label.
- Split seed: 2026. Split assignments are in `data/processed/splits_v0.parquet`.
- Every model is fit on the same train rows and scored on the same validation rows. No prompt group crosses the split.

This implementation does **not** use five-fold OOF or a separate holdout. V0.2 must preserve the current split hash and validation IDs; do not recreate the split as part of model training. The validation set is used repeatedly to monitor epochs and compare models, so later scores are development measurements and may become optimistic after selection.

### Existing validation baseline

The clean restart recorded these balanced accuracies on the 540 validation rows:

| Experiment | Balanced accuracy |
|---|---:|
| SVC, raw decision scores | 0.3074 |
| UltraBERT-380M | 0.3444 |
| Qwen3-0.6B | 0.3444 |
| Equal-weight SVC + UltraBERT-380M + Qwen3-0.6B | 0.3648 |
| Train-fitted weighted SVC + UltraBERT-380M + Qwen3-0.6B | 0.3481 |

The train-fitted weights were 0.9 SVC, 0.1 Qwen3-0.6B, and 0 UltraBERT-380M. They were fitted from train-row predictions only; validation labels were not used to select them. The equal-weight blend is the current baseline to beat on validation.

Each model remains a configurable model parameter with its own YAML config, immutable Hugging Face revision, output directory, experiment ID, and predictions. SmolLM3 uses the shared causal-LM LoRA path and configured attention projections. Granite H Micro uses the same classification head with LoRA on q/k/v/o attention projections and in/out Mamba projections. EmbeddingGemma 2 uses its classification task prefix, masked mean pooling, and L2 normalization. The other multimodal models use their text components with masked mean pooling. Keep all Hub access out of training and load the pinned local snapshots offline. LoRA is a later option for the frozen-backbone candidates if their baselines justify the extra training cost.

## 4. Training and epoch validation

Train Qwen17 and Qwen4 **separately** on the full 2,159-row train partition for 10 epochs each. Start each from its own pretrained base checkpoint; do not initialize either model from Qwen06 or from the other new model.

Train SmolLM3-3B Base as a separate 10-epoch causal-LM run on the same train partition, with validation after each epoch. Use the shared LoRA readout and its own pinned tokenizer/checkpoint. The current config starts at microbatch 1, probes up to 128, uses gradient accumulation 8, and enables gradient checkpointing; record the probe-selected batch and resulting effective batch in the manifest.

Train Granite 4.0 H Micro Base as its own 10-epoch run after a load/gradient smoke test. Its hybrid design has only four attention layers and 36 Mamba2 layers, so target LoRA adapters at both attention and Mamba input/output projections; use the same split and per-epoch validation reporting.

Reuse the existing Qwen classifier design:

- LoRA adapters on configured attention projections.
- Masked-mean pooling over the final hidden state.
- A supervised 18-class linear readout with the canonical label order.
- Temperature calibration fitted from train predictions only after training.
- Fixed seed, tokenizer, maximum length, and validation row order for comparable runs.

At the end of **each epoch**, evaluate on all 540 validation rows and record:

- Ordinary accuracy.
- Balanced accuracy (primary metric).
- Validation loss and macro-F1 where supported.
- Epoch number and elapsed training time.

Run all 10 epochs; validation measurement does not feed gradients, learning-rate scheduling, or optimizer updates. Save the epoch metrics in the experiment manifest and training log. Save an epoch checkpoint or adapter snapshot. Select the checkpoint with the highest **ordinary validation accuracy**; break ties by choosing the earliest epoch. Report the selected epoch and epoch 10. This is model selection on the development validation split and must be labeled as such.

The final model prediction file must contain the same validation IDs and 18 probability columns as the other models. Record raw logits/scores separately from calibrated probabilities. Calculate validation balanced accuracy both from raw logits and calibrated probabilities at the final checkpoint, as the existing evaluation factory does.

## 5. Initial hardware recipes

Use the local CUDA 13.x Python environment and train one Qwen model at a time on the RTX 5070 Ti. These settings are starting points; verify memory on a short smoke run before committing to the 10-epoch run.

| Setting | Qwen17 | Qwen4 |
|---|---:|---:|
| Epochs | 10 | 10 |
| Maximum length | 384 | 384 |
| LoRA rank / alpha / dropout | 16 / 32 / 0.05 | 16 / 32 / 0.05 |
| Learning rate | 1e-4 initial | 1e-4 initial |
| Microbatch | 2 | 1 |
| Gradient accumulation | 4 | 8 |
| Precision | BF16 when supported, otherwise FP16 | BF16 when supported, otherwise FP16 |
| Memory fallback | Gradient checkpointing if needed | Gradient checkpointing; use 4-bit QLoRA only if required and record it |

The effective batch size is 8 in both initial recipes. Record actual precision, quantization, peak VRAM, fit duration, inference throughput, and checkpoint size. If the current trainer does not expose a required memory option, add the smallest shared option to the configurable Qwen factory rather than duplicating its implementation.

## 6. Ensemble experiments

Reuse the existing equal-probability averaging and train-only weight fitting. Do not fit weights from validation labels. All ensemble outputs must align by validation ID and class order.

First compare the new standalone models and the direct Qwen combinations:

| Experiment | Model set | Question |
|---|---|---|
| V02-E0 | SVC + UltraBERT-380M + Qwen06 | Fixed existing equal-weight baseline |
| V02-E1 | Qwen17 | Does the 1.7B model improve over Qwen06 alone? |
| V02-E2 | Qwen4 | Does the 4B model improve over Qwen06 and Qwen17 alone? |
| V02-E3 | Qwen06 + Qwen17 | Does Qwen17 add complementary errors to Qwen06? |
| V02-E4 | Qwen06 + Qwen4 | Does Qwen4 add complementary errors to Qwen06? |
| V02-E5 | Qwen17 + Qwen4 | Do the two new sizes complement one another? |
| V02-E6 | Qwen06 + Qwen17 + Qwen4 | Does the three-size Qwen blend help? |

Then add the new models to the existing model roster:

| Experiment | Model set |
|---|---|
| V02-E7 | SVC + UltraBERT-380M + Qwen06 + Qwen17 |
| V02-E8 | SVC + UltraBERT-380M + Qwen06 + Qwen4 |
| V02-E9 | SVC + UltraBERT-380M + Qwen06 + Qwen17 + Qwen4 |

After the Qwen comparisons, extend the ensemble matrix with each Gemma candidate individually, both Gemmas together, and each Gemma paired with the strongest existing equal-weight roster. Also compare the full roster only if every member has aligned validation predictions. For each combination, include equal averaging and weights fitted from training predictions only. Report adapter/resource blocks explicitly rather than omitting either Gemma from the scope.

For each applicable roster, report equal weights and train-fitted weights side by side. The train-fitted weights must be selected from training predictions only, frozen before validation scoring, and stored with their training objective and model roster. Treat in-sample train metrics as descriptive; use validation metrics to assess whether those weights transfer. Report the weighted result as an additional metric, not as a replacement for the equal-weight baseline.

## 7. Reporting and decision criteria

For each model and ensemble, report validation ordinary accuracy, balanced accuracy, macro-F1, log loss, per-class recall, confusion matrix, fit time, inference time, peak VRAM, and artifact size. For ensembles, also report their delta versus E0, pairwise disagreement, unique correct examples, and prompt-group paired bootstrap intervals.

Show ordinary and balanced accuracy by epoch as a table or curve, mark the selected highest-accuracy checkpoint, and compare it with epoch 10. CatBoost has no epochs; retain the boosting iteration with highest validation accuracy. Compare each new model and combination with the fixed equal-weight E0 score of 0.3648. Do not claim a model-size improvement from a small validation difference without considering prompt-group uncertainty and class-level regressions.

Keep the selected checkpoint and model roster explicit. Kaggle inference uses the saved checkpoint selected from validation or continuation runs; do not train another model on all labelled rows after selection.

## 8. Implementation sequence

1. Freeze and verify the current split hash, class order, baseline experiment IDs, and baseline prediction files.
2. Add `qwen17` and `qwen4` model configs and register their IDs in the CLI/model factory.
3. Ensure the shared Qwen trainer supports per-epoch validation metrics and epoch checkpoint snapshots.
4. Run a short memory smoke check for each new backbone, then train Qwen17 for 10 epochs and Qwen4 for 10 epochs sequentially.
5. Add `smollm3_3b` to the pinned configs and shared causal-LM LoRA path; smoke-test load, memory, training, and offline inference before its 10-epoch run.
6. Add and smoke-test the `granite4_h_micro` adapters against both attention and Mamba layers before its 10-epoch run.
7. Smoke-test the `embeddinggemma2`, `gemma4_e4b`, and `ministral3_3b` frozen-backbone paths for load, memory, aligned predictions, and offline inference before full evaluation.
8. Verify each run’s epoch count, validation IDs, classes, checkpoint files, and per-epoch metrics.
9. Evaluate the Qwen ensemble matrix and the SmolLM3/Granite/Gemma/Ministral extensions with equal and train-fitted weights; append distinct experiments to the registry without deleting the existing baseline.
10. Show per-epoch scores and ensemble comparisons in the dashboard, with split and validation row count clearly labeled.

## 9. Definition of done

- The original V0 data and split artifacts remain unchanged.
- Qwen17 and Qwen4 each complete 10 epochs on the same 2,159 train rows and record validation results after every epoch on the same 540 rows.
- Their final and best-epoch checkpoints, configs, immutable revisions, metrics, and predictions are saved under distinct experiment IDs.
- The specified Qwen combinations and baseline additions are evaluated from exactly aligned validation predictions.
- SmolLM3-3B completes its 10-epoch run with per-epoch validation metrics, or has a specific documented runtime/access block.
- Granite 4.0 H Micro Base completes its 10-epoch run with per-epoch validation metrics, or has a specific documented runtime/access block.
- EmbeddingGemma 2, Gemma 4 E4B, and Ministral 3 3B each have a recorded smoke-test/training result or a specific documented runtime/access block; any completed predictions are aligned to the same validation IDs and classes.
- SmolLM3, Granite, Gemma, and Ministral candidates are compared standalone and in ensembles using equal weights and weights fitted only on training predictions.
- Equal-weight and train-fitted weighted metrics are both reported; validation labels are not used to fit weights.
- The dashboard and registry identify each backbone by name and expose epoch accuracy, validation accuracy, and ensemble membership.
